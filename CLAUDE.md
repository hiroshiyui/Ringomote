# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project goal

Ringomote is an Android app that makes the phone act as an Apple TV remote, compatible with the 1st-generation Siri Remote, so the Apple TV can be controlled directly from the phone (no Wi-Fi/companion-protocol bridge; the phone itself is the remote).

## Architecture

Layers, with dependencies pointing downward only (`ui → remote → hid ← bluetooth`):

- `hid/` — pure Kotlin, no Android imports. The HID report descriptor (`HidReportDescriptor`, annotated byte by byte), report encoders (`HidReports`), usage constants, and the `HidReportSink` interface. Two input reports: ID 1 keyboard (8 bytes, 6-key array) and ID 2 consumer control (one 16-bit usage). Changing the descriptor means changing the encoders and the descriptor-parsing tests together.
- `remote/` — pure Kotlin. `RemoteControl` (the Siri Remote controls), `HidKeyMap` (control → HID usage; arrows/Enter/Escape on the keyboard page, Home/Play-Pause/Volume/Mute on the consumer page), and `RemoteSession`, which tracks held controls and turns press/release into reports. Invariant: every press is eventually released; `releaseAll()` runs when input stops (app stopped, disconnect, ViewModel cleared) so the Apple TV never sees a stuck key.
- `bluetooth/` — Android-specific. `HidTransport` interface (state as `StateFlow<TransportState>`, start/stop, connect/disconnect, also a `HidReportSink`). The live implementation is `BleHidTransport`: BLE HID over GATT (HOGP), the phone as peripheral. It is a thin adapter over `BluetoothGattServer` + `BluetoothLeAdvertiser`; the GATT layout (Device Information, Battery, HID services with one input Report per report ID) is built by `HidGattServices`, and the connection state machine and its recovery rules (advertising while no host, stop advertising while one is connected, bonded hosts count as subscribed, Bluetooth off/on) live in `BleLinkController`, pure Kotlin behind `BlePeripheralPort`, unit-tested with a fake. `TransportState.Connected` means the host has subscribed to the input reports, not merely that the link is up. `BluetoothHidDeviceTransport` + `HidLinkController` (classic Bluetooth HID) are kept as an alternative implementation but are not wired in. Put new connection logic in the controllers, not the transports. `BluetoothPermissions` centralises the API-31 permission split.
- `ui/` — Compose. `RemoteViewModel` runs everything that touches the transport (input, connect, start/stop) on `AppContainer.serialDispatcher`, shared app-wide, so report order is kept, binder calls stay off the main thread, and a closing screen's stop cannot overtake the next screen's start. It also releases held controls whenever the link leaves `Connected`. Screens depend only on the ViewModel and state types. `RingomoteApp` has three tabs: the remote, `ui/settings/SettingsScreen` and `ui/about/AboutScreen`; the About texts (privacy, license, open-source notices, trademarks) summarise `LICENSE`, `NOTICES.md` and the README, so update them together, in all three locales (`values`, `values-zh-rTW`, `values-ja`).
- `settings/` — `AppearanceSettings`: theme mode (System/Light/Dark) and dynamic colour, in SharedPreferences, published as a `StateFlow`. `MainActivity` feeds it to `RingomoteTheme`, which picks dynamic colours on Android 12+ when asked, else the coral `RingomoteLightColors`/`RingomoteDarkColors` in `ui/theme/Color.kt`. `ui/settings/SettingsScreen` is the Settings tab. Never hard-code colours in screens; use `MaterialTheme.colorScheme` roles so all three schemes work.
- `diagnostics/` — `EventLog`, a bounded in-memory ring buffer the BLE transport records link events into (server, services, advertising, host connect/disconnect with HCI status, descriptor writes, failed notifications), and `DiagnosticsReport`, which prints it with the app, device, adapter, permission, transport-state and paired-device facts. Settings > Advanced shows it in `ui/settings/DiagnosticsScreen` with copy, share and save; nothing leaves the phone otherwise. Record new link events in the transport, not the controller, so the pure controller stays free of logging.
- `network/` — the only network use in the app, all behind the opt-in `NetworkSettings` switch (Settings > Network). `AppleTvDiscovery` (interface; pure Kotlin helpers `CompanionLink`/`AppleTvModels`, unit-tested) finds Apple TVs through Bonjour; `NsdAppleTvDiscovery` implements it on `NsdManager`, browsing `_companion-link._tcp` and keeping services whose `rpMd` starts with `AppleTV`, with a multicast lock held while browsing; `RingomoteApp` starts it only while the Settings tab shows the list. `LocalNetwork` binds sockets to the non-VPN Wi-Fi/Ethernet network. `network/companion/` is the Companion Link client that wakes a sleeping Apple TV (which does not listen for BLE and ignores Wake-on-LAN): pure Kotlin `Tlv8`, `Opack`, `HapSrpClient` (SRP-6a, tested against srptools vectors), `PairSetup`/`PairVerify` (HAP, transport-free state machines over TLV bytes), `CompanionCredentials`; `HapCrypto` wraps Bouncy Castle's lightweight API (never register its JCA provider); `CompanionClient` is the blocking framed/encrypted socket client (run on `Dispatchers.IO`); `CompanionCredentialsStore` keeps pairings per Bonjour service name, excluded from backups. `ui/settings/AppleTvViewModel` drives Pair → PIN → Wake/Forget per row. Protocol notes and hardware findings: `docs/companion-link.md`. Manifest: `INTERNET`, `ACCESS_NETWORK_STATE`, `CHANGE_WIFI_MULTICAST_STATE`.
- `history/` — `ConnectionHistory`: one persisted boolean, "has ever connected to a host" (Android can't tell an Apple TV from other bonded devices, so this stands in for "Apple TV paired"). The connection panel auto-expands its pairing details until it is true.
- `AppContainer` (created by `RingomoteApplication`) is manual DI: process-lifetime transport, session, serial dispatcher and application scope. Swap implementations there.

Transport decision: BLE HID over GATT, chosen after a hardware check on 2026-11-03. Classic Bluetooth HID (`BluetoothHidDevice`) registers fine on Android, but tvOS never lists the phone: it filters classic devices by class of device, and Android reports "phone", which an app cannot change. With BLE the Apple TV lists the phone at once, pairs (a consent prompt, then a 6-digit comparison that Android shows only as a notification when another app is in front — the pairing hint says so), reads the report map, subscribes to both input reports and acts on keyboard report notifications (arrow Right verified). Both implementations stay behind `HidTransport`. The Apple TV sees the phone's Bluetooth name. The touch surface is emulated with discrete arrow keys; Siri voice input is not reproduced.

Verified on hardware (Nokia G50, Android 13): discovery, pairing, subscription, the touch surface (arrow keys), Select, Menu (Escape), TV/Home (Data On Screen 0x60: tap goes Home, a hold of 1.5 s opens Control Center; AC Home 0x223 also goes Home but never opens Control Center), Play/Pause and Volume. The 2nd-gen Siri Remote's own usages, from a macOS project that reads it: TV 0x60, Select 0x80, Back = Generic Desktop 0x86, Mute 0xE2, Power 0x30, Siri 0x04, Menu Up/Down/Left/Right 0x42–0x45. Link rules found on 2026-11-04/05: the Apple TV owns the link. It reconnects by itself when awake and the phone advertises. A phone-side connect from the GATT server opens a *classic* (BR/EDR) link, because the TV is dual-mode and Android picks that transport; the TV closes it within a second, so the Connect button and the BLE transport's `connect()` were removed (the classic transport keeps its own). A server-side `cancelConnection` only detaches this server; the TV keeps the LE link up. **The process must not die while the TV is connected**: when it does, the stack deletes the services and sends Service Changed, and tvOS then drops the keyboard and never rediscovers it on that link, even if a new process re-adds the services on identical handles; only a fresh link (Bluetooth off/on on the phone, or the TV sleeping and waking) makes it re-check and subscribe again, with no re-pair. Hence `service/RemoteService`, a foreground service (type connectedDevice, with a Stop action) that keeps the process and the transport alive once started, and `service/BootReceiver`, which starts it again after a reboot unless Stop was tapped (a "wanted" flag in SharedPreferences); `RemoteViewModel` no longer stops the transport. If the process was killed anyway, a bonded host that was connected before the services existed is shown as `TransportState.Resyncing`. Left alone, tvOS recovers by itself: about 20–30 s after the Service Changed it drops the link, re-makes it and re-enumerates (writes the CCC descriptors again), seen twice on 2026-11-05 (23:22 and 23:56). Every attempt to hurry it (reopening the server, dropping the link from the phone with a GATT-client disconnect) prevented that recovery, so the controller must do nothing but wait; the UI says so and offers a Bluetooth toggle, then Forget and re-pair, as fallbacks. GATT handles are also not stable across server opens (the pool is shared with other apps); the controller saves the layout at subscription time and shows Resyncing on a mismatch until the host subscribes again; it never closes and reopens the server to chase handles, because a host may already be attached and deleting services under its link is the very thing that kills the keyboard. The TV copes with moved handles on a fresh link. Bluetooth behaviour cannot be tested on the emulator.

- Android 12+ (API 31) needs the runtime permissions `BLUETOOTH_CONNECT` / `BLUETOOTH_ADVERTISE`; Android 9–11 use install-time `BLUETOOTH` / `BLUETOOTH_ADMIN` (`maxSdkVersion="30"`).

## Build & test commands

```bash
./gradlew assembleDebug                 # build debug APK
./gradlew installDebug                  # build and install on a connected device
./gradlew lint                          # Android lint
./gradlew testDebugUnitTest             # JVM unit tests (app/src/test)
./gradlew connectedDebugAndroidTest     # instrumented tests on a device (app/src/androidTest)

# single test class / method
./gradlew testDebugUnitTest --tests "org.ghostsinthelab.app.ringomote.remote.RemoteSessionTest"
./gradlew testDebugUnitTest --tests "org.ghostsinthelab.app.ringomote.remote.RemoteSessionTest.<method>"
./gradlew connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=<fully.qualified.TestClass>
```

## Build setup notes

- Single module `:app`, package/namespace `org.ghostsinthelab.app.ringomote`. UI is Jetpack Compose with Material 3; theme lives in `ui/theme/`.
- Dependencies and plugin versions are managed in `gradle/libs.versions.toml`; add new dependencies there and reference them via `libs.*`.
- AGP 9 is used: Kotlin support is built into AGP, so there is no `org.jetbrains.kotlin.android` plugin. Only `kotlin.compose` is applied. Do not add the Kotlin Android plugin.
- R8 is configured with the AGP 9 `optimization { }` DSL in the `release` build type. Keep rules go in `app/src/main/keepRules/` (all files there are merged), not in `proguard-rules.pro`.
- compileSdk/targetSdk 37, Java/JVM target 11. Gradle configuration cache is enabled.
